A support model that knows what a margin call is.

Tickdesk is an end-to-end fine-tuned LLM customer support platform for an online trading broker — data pipeline, LoRA fine-tune, hybrid retrieval, tool-calling agent, safety layer, eval harness and serving, built as one system rather than a prompt in a notebook. A general-purpose model answers a withdrawal-delay ticket with an apology. This one checks the payment-agent status, cites the policy clause, and escalates when the account is under compliance review.

01

Why a general model loses money on this desk

Brokerage support is a narrow domain with wide consequences. The failure modes are specific, and each one is a reason to own the model rather than rent a prompt.

Vocabulary

The jargon is load-bearing

Swap rate, stop-out level, pip value, payment agent, negative-balance protection, KYC tier. A base model paraphrases these into plausible nonsense; the difference between "margin call" and "stop out" decides whether a client's position was closed correctly.

Regulation

Some answers are illegal

The model must never recommend a trade, predict a market, promise a return, or discuss a product not licensed in the client's jurisdiction. That is a hard behavioural constraint, and fine-tuning plus a policy filter enforces it far more reliably than a system prompt that a user can argue with.

Format

Tickets are not chat

Real tickets arrive as a screenshot, a half-sentence in a second language, and an account ID. The tuned model learns this distribution — terse, code-switched, evidence-attached — instead of the polite full-sentence prose an instruct model expects.

Grounding

The answer lives in account state

"Where is my withdrawal" cannot be answered from documents. It needs a tool call against the payments service, a policy lookup for the SLA, and a decision about whether the delay is normal. Retrieval alone gets you a paragraph about withdrawals in general.

Cost

Volume changes the arithmetic

At a few hundred thousand conversations a month, the gap between a frontier API and a tuned 7B served on your own GPUs is the entire budget. A distilled model that matches the teacher on this narrow domain is the whole point of fine-tuning.

Adversaries

Clients have an incentive

Support for a financial product attracts prompt injection and social engineering aimed at account access, bonus abuse and fee waivers. The system assumes the user is untrusted input, not an operator.

Design note

Rejected samples are handwritten, not scraped

The behaviours worth training away are rare in real transcripts because agents rarely commit them. So the rejected side of each preference pair is generated deliberately: ask the base model the question with the guardrails removed and keep the answers that are confidently wrong in a specific, recognisable way.

Design note

Redaction runs before anything else touches the text

PII removal is the first transform in the DAG, not a step before release. Every downstream artefact — embeddings, eval sets, judge prompts, trace payloads — is derived from redacted text, so nothing sensitive can leak into a vector index or a log that outlives the ticket.

Fine-tuning and serving

A 7B base, tuned twice: supervised on the domain, then preference-aligned on the behaviours a support model must refuse. Everything fits on one 48GB card, which is the point — the whole thing is reproducible on rented compute for the cost of a weekend.

05

Retrieval that survives a real knowledge base

The corpus is help-centre articles, T&Cs, payment-method matrices and internal agent macros — dense, versioned, and full of near-identical pages per jurisdiction. Dense retrieval alone confuses them; BM25 alone misses paraphrase. So, both.

Chunking

Structure-aware, not fixed-size

Split on document headings with a 900-token cap and 15% overlap; each chunk carries its breadcrumb, jurisdiction tag, product tag and effective date as metadata. A chunk that has lost its heading has lost the only thing distinguishing it from four sibling documents.

Hybrid search

BM25 + BGE-M3, fused with RRF

Sparse catches exact error codes and product names ("error 10014", "MT5 hedging"); dense catches "my money is stuck". Reciprocal rank fusion at k=60 merges the lists without tuning a weight per query type.

Reranking

Cross-encoder to top-5

bge-reranker-v2-m3 over the top 40 fused candidates. This is the single largest quality lever in the pipeline and the one most often skipped — it lifts recall@5 far more than any embedding upgrade.

Filtering

Metadata before semantics

Jurisdiction and account-tier filters are applied as hard pre-filters. A client in one regulatory entity must never be shown another entity's leverage limits, and that is a filter predicate, not something to ask the model to be careful about.

Freshness

Effective-dated chunks

Policies supersede each other. Chunks carry validity windows, superseded versions are excluded at query time but retained for answering "what was the fee in March", and index rebuilds are incremental on document change events.

Grounding

Citations are enforced, not requested

The model emits claims with chunk IDs in a structured field. A post-check verifies every ID exists in the retrieved set; an answer citing a chunk that was never retrieved is dropped and regenerated once, then escalated.

Tools, schemas and the escalation contract

The agent loop is deliberately shallow — plan, at most three tool calls, answer — because deep autonomous loops in a financial context fail in ways that are expensive and hard to audit. Every tool is read-only except escalation.

Escalation policy

Four triggers, all deterministic

  • Intent confidence below 0.75, or no chunk above the rerank floor
  • Any complaint, regulator mention, or loss claim — routed to a human by rule, never answered
  • Tool failure or timeout on a fact the answer depends on
  • Second turn on the same unresolved issue — one retry, then a person
Degradation

What happens when a dependency is down

If the payments service times out, the model does not guess from the knowledge base. It says what it could not check, gives the published SLA, and offers escalation in the same turn. A support system that invents a transaction status is worse than one that is briefly unhelpful.

07

Safety, privacy and the red-team harness

Four layers, ordered by cost: cheap deterministic checks run first so the expensive model never sees traffic it should refuse. Each layer is separately testable and separately logged.

Critical
Prompt injection via ticket attachments and pasted content
Clients paste emails, chat logs and screenshots with OCR'd text. All of it is wrapped in delimited untrusted blocks with an instruction-hierarchy prompt, and a classifier scores injection likelihood before the turn runs. Tool arguments are never taken verbatim from user text — the account ID always comes from the session, never from the message.
Critical
Financial advice and return promises
An output classifier trained on the DPO rejected set flags recommendation, prediction and guarantee language. A flagged answer is regenerated once under a stricter template, then escalated. This is the constraint the DPO stage exists to bake into the weights so the filter is a backstop, not the only defence.
High
PII leakage into logs, traces and indexes
Redaction at ingest, redaction again on the inbound live turn, and trace payloads stored as redacted text with reversible tokens held in a separate keyed store. Reviewers see ⟪ACCT⟫; only an authorised de-tokenisation call resolves it, and that call is itself audited.
High
Social engineering toward account access
The model cannot perform any state-changing action, so the worst case of a successful manipulation is a disclosure. Disclosure is bounded by session scoping: every tool is authorised server-side against the session, and "my friend's account" simply has no reachable data path.
Managed
Silent quality drift
Retrieval score distributions, refusal rate, escalation rate and answer-length distribution are tracked per intent with alerts on distribution shift. A knowledge-base edit that quietly breaks retrieval for one product shows up as a recall drop within a day, not as a complaint next quarter.
Red team

180 adversarial cases, run on every release

Direct jailbreaks, indirect injection in pasted content, multilingual evasion, roleplay framing, incremental extraction across turns, and authority spoofing ("this is the compliance team"). The suite is a CI gate: a release that regresses on any critical-severity case does not promote, regardless of how good its quality metrics look.

Auditability

Every answer is reconstructable

Each turn logs adapter version, prompt template version, index version, retrieved chunk IDs with scores, the full tool trace, guardrail verdicts and the final output. Given a complaint six months later, you can rebuild exactly what the model saw and why it said what it said — which is the actual requirement in a regulated business.

A 500-case golden set, hand-labelled and stratified across the intent taxonomy, plus component-level suites. Nothing promotes on vibes; the harness runs in CI and every metric has a gate.

Ablations

Every component earns its place

The harness runs the same golden set against base + RAG, SFT only, SFT + DPO, and the full stack with and without reranking. The deliverable is a table showing what each stage bought — including any stage that bought nothing and was cut.

Judge discipline

The judge is validated too

LLM-as-judge agreement with human labels is measured on a held-out slice before the judge's scores are trusted. Position bias controlled by randomising order; ties reported rather than broken.

Online

Shadow first, then a slice

A candidate adapter serves shadow traffic with outputs logged but not shown, compared on agreement and escalation rate. Promotion to 5% live traffic, then full, with automatic rollback on escalation-rate regression.

09

Build plan

Sequenced so there is something demonstrable at the end of every phase, and so the eval harness exists before the model it judges.

Week 1 · in progress

Corpus and harness

Synthetic ticket generation, redaction pipeline, intent taxonomy, grouped splits, and the golden set with its gates — written before any training, so the first model has something to fail against.

Week 2

Retrieval baseline

Chunking, hybrid index, reranker, citation enforcement. Measured against the golden set with a base model and no fine-tuning — this is the number everything later has to beat.

Week 3

SFT and DPO

QLoRA run, adapter registry, DPO on the preference set, ablation table across the four configurations.

Week 4

Agent loop and guardrails

Tool adapters with schema contracts and session scoping, escalation rules, the four guardrail layers, red-team suite wired into CI.

Week 5

Serving and observability

vLLM with LoRA hot-swap, OTel tracing, cost and drift dashboards, shadow-serving path, and a demo UI that shows the trace beside every answer.

Week 6

Write-up

Final eval report with the ablation table, a short technical post on what the DPO stage actually changed, and the repo cleaned to a one-command reproduction.
